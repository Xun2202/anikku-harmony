## 修了什么

官方 Anikku Preview 在卓易通里下载任何一集都会反复失败并提示 `Error in ffmpeg!`。日志里的根因是：

```
E ffmpeg-kit: Failed to open SAF id: 8 ... IllegalArgumentException: Failed to determine if
  primary:Documents/Anikku/downloads/<源>/<标题>/Video_tmp/Video.tmp is child of primary:Documents/Anikku:
  java.io.FileNotFoundException: Missing file for ... Video.tmp
```

Anikku 先在用户选择的 SAF 目录里创建 `Video.tmp`，再把这个 `content://` URI 交给 ffmpeg-kit 的 `saf:` 协议去打开；
卓易通的文件提供方在打开时找不到刚建好的文档，ffmpeg 直接失败。上游 Aniyomi 也有同样的报告（[aniyomiorg/aniyomi#2126](https://github.com/aniyomiorg/aniyomi/issues/2126)，Motorola 设备），至今未修。
此外卓易通不支持 SAF `renameDocument`，就算下载成功，`<集>_tmp` 目录也改不了名。

本构建的做法：ffmpeg 改写到 App 私有缓存里的普通文件，写完后再复制进下载目录；目录/文件改名失败时自动改为「复制后删除」。
另外提供「使用应用私有目录」一键选项，完全绕开 SAF。

- **「检查更新」可能一直停在旧版本**（preview.12 及之前）：更新器取 Release 列表里的第一项，GitHub 的列表顺序不保证按版本（Mihon 在上游 0.21.0 → 0.21.1 时实际中招）。preview.13（补丁 0024）起按版本号取最大。
- 书架 / 浏览页显示模式新增「**全景紧凑网格**」（preview.13，补丁 0022）；瀑布流里右侧快速滚动条不再抽搐（补丁 0023）。
- **全景网格滑动时格子抽搐、有掉帧、滚动条还在跳一下**（preview.13 及之前）：格子第一次出现时还不知道封面是横是竖，先按默认横版（3:2）排，图片解码完才改成竖版（2:3）。瀑布流里一个格子变高，会把这一列下面的全部推下去；快速滑动时每秒几十张图加载完，各触发一次整个瀑布流重新测量。横竖比例只记在内存里，重启 App 就忘了。横版和竖版封面还是两段不同的界面代码，一切换就把图片拆掉重新请求。滚动条用的是屏幕上看得见的格子高度，高度在滑的时候变，估算就跟着跳（补丁 0023 的滚动条算法本身没改）。preview.14（补丁 0025）起：学到的高/宽写进 App 自己的文件，下次启动直接用；正在滑动时不把新学到的形状写进排版（已经能确定是横还是竖的，马上用）；横版和竖版走同一个封面组件。从没见过的封面仍会在你手指停下的那一下改一次形状，改完就记住了。和 Mihon preview.3 是同一份代码。滑动还掉不掉帧，要在真机上滑一下确认。
- **全景紧凑网格比 Mihon 卡、滑块发顿**（preview.14）：Anikku 的封面（从 Komikku 继承的 `MangaCover`）用 Coil 的 `SubcomposeAsyncImage`。这种画法会让懒加载网格里的每个格子再套一层界面，Coil 的文档也说它不适合放进懒加载列表；每个还在加载的格子都画一个不停转的圆圈，每一帧都在画。Mihon 的封面本来就是普通 `AsyncImage` 加一块底色，所以同样的全景紧凑网格 Mihon 先觉得丝滑。preview.15（补丁 0026）起：封面改在同一块底色里用 `AsyncImage` 画，出错时把图标画在色块上；转圈要等封面超过 400 毫秒还没出来才出现，内存或磁盘里已经有的封面不会闪一下转圈。来源角标不再每次重读 `Source.icon`（那个取值会去扫已装扩展，还可能把图标重画成一张新图），按来源 id 记住。Mihon 没有这层（封面已是 `AsyncImage`，也没有来源角标）。Animeko 没有这套网格。
- **拖快速滚动条、两下甩动之间全景格子还会跳一下，浏览页新格子第一次出现也会改形状**（preview.14，和 Mihon preview.3 同一处）：上一版把「网格算不算停下来」写成「手指没在滑」。拖右侧快速滚动条时，两下跳动之间它以为已经停下，刚学到的横竖就写进排版；连续甩两下、中间停一下，也一样。浏览某一图源时，封面要等格子出现在屏幕上才去学横竖。preview.15（补丁 0027）起：要连续 300 毫秒没有任何滚动，才把新形状写进排版；浏览页对已经加载、还没上屏的封面提前要一张 128 像素的小图并记下高/宽。相关作品页只用这个 300 毫秒判断（列表短，不提前下载）。`PanoramaCoverShapes.kt` 与 Mihon 0019 逐字节相同。刚打开浏览页的第一屏仍可能改一次形状；某张封面下载失败就一直是默认横版。拖滚动条和滑动还抖不抖，要在真机上确认。
- **全景网格往下滑动时，右侧滑动块大约每一行往回抽一下**（preview.15，和 Mihon preview.4 同一处）：上一版修的是格子的形状和封面转圈，滚动条怎么算位置没有改。瀑布流每一列格子高矮不一样。旧算法拿屏幕上编号最小的那一格当基准；这一格滑出屏幕就换成下一格，每一格的误差不一样，所以大约每过一行，拇指会顺滑下滑一小段，然后突然往上抽一丝，再移回来。preview.16（补丁 0028）起和 Mihon 补丁 0020 是同一段代码：记住一个两帧之间都还在屏幕上的格子，用它实际移动了多少来推动拇指；最上面那一项还看得见时用精确位置；拖拇指或跳转之后这个基准不在了，才退回原来的算法。手指还在滑的时候先不改「整份列表有多长」；松手后拇指用 150 毫秒平滑移到新位置；滑到最底时拇指在最底。顺不顺要在真机上往下看一眼。0030 起这套估算已删除，滚动条改用真实列表高度，见下一条。
- **全景网格最后一个总跑到右边、左边空一块；折叠屏展开后要滑一下格子才排好**（preview.16，和 Mihon preview.2 同一处）：系统自带的瀑布流把下一项放进当前最矮的那一列，右边只矮一丝也会放右边，左边就空出一块。列数一变（两列变四列）时，又把屏幕上看得见的几项当成新的开头，停在列表中部时最后几项和前面空一格，要再滑一下才重排。preview.17（补丁 0030）起和 Mihon 补丁 0021 是同一套自己排的瀑布流：下一项放进最左边、底边还没比最短列高出「这项一半高度」的那一列；列数或宽度变的同一帧就按整份列表重排，并钉住你正在看的那一项，不跳回顶部。右侧快速滚动条改为用列表的真实高度，不再估算（补丁 0028 那套估算去掉了）。书架、浏览页、相关作品页都改了。模拟器上看过：长列表末尾左边不再空一块；把屏幕改宽的当帧就变成四列，改回去也不跳到最顶；快速滚动条拖得动；书架下拉刷新、浏览翻页正常。真折叠屏只在模拟器里用改分辨率模拟过，惯性滑动手感要在手机上再看一眼。
- **书架里点进一个资源，退出来回到最顶；松手后一卡一卡；按住滚动条会变透明并变成上翻；折叠屏自动只有两列**（preview.17，和 Mihon preview.4 同一处）：四件事一起修，preview.18（补丁 0031–0037）起，与 mihon-harmony 0023–0029 一一对应、同源。① 滚动位置记在父界面的副作用里，手指滑动不会让父界面重算，记下的永远是顶部；进详情页后这一页被拆掉，回来就按 0 恢复。现在按作品自己的 key 记住位置，列表加载完整后再恢复。书架、浏览、相关作品的全景都改了。② 任一封面加载完都会让整屏重排；布局缓存命中时，每一帧仍要把全部条目各算一遍高度。内容没变就跳过逐项计算（2000 项、120 帧：每帧 0.323 ms → 0.0082 ms，每帧分配 266,776 B → 56 B）。封面形状改成按版本通知，跨过横竖分界要等网格停稳 300 ms 才一次提交。瀑布流滚动条不再每帧拆掉重建；番剧详情页剧集网格的滚动条同样改了。③ 滚动条只在拇指还看得见时才接手势。按住不动时拇指淡出，手势落到封面上，就被当成往下滑，列表反而上翻。现在按下就抓住，按住期间不淡出、不放手势，触摸区 32 dp。④ 自动最小列宽原来是 168 dp，360 dp 宽只有 2 列。现在按网格自己的宽度分档：不到 600 dp 用 112 dp，600 dp 及以上用 140 dp。横封面在 3 列及以上时横跨两列。这一版没有真机或模拟器上的手势测试，返回是否回到原位、惯性是否顺、按住滚动条能否直接拖（含番剧详情页的剧集网格）、折叠和展开的列数，要在手机上确认。
- **折叠屏全景紧凑右边空一列；滑到书架最底再往回甩，惯性有时没了**（preview.18，和 Mihon preview.5 同一处）：两件事一起修，preview.19（补丁 0038–0040）起，与 mihon-harmony 0030–0032 一一对应、同源。① 折叠竖屏大约 459 dp，按上一版的分档是 3 列。横封面在 3 列及以上时横跨两列，两组一样高时放最左边。横封面占多数时，第 3 列永远没有东西可放，看起来右边空着、只剩一列。Mihon 竖封面多，竖封面会填上第 3 列，所以那边平时看不出来。新规则不按应用、也不按横着拿还是竖着拿写死列数：每张封面看起来差不多大，这一格网格上哪种封面多，列宽就按那种来。竖封面为主时，展开竖着拿仍大约 4 列。横封面为主时，折叠竖屏是 2 列宽封面，不再空一列；展开横着拿从一屏大约 6 张跨列变成大约 11 张不跨列。形状还没学够时先按上一版的分档显示，判定之后最多跳一次，你正在看的那一项还在原位。你自己固定了列数时，列数不变，跨不跨列仍按这一格的主导形状。书架、浏览、相关作品的全景都按自己这一格来统计。② 上一版把滚动条可点的区域加宽到 32 dp，画出来的拇指大约 12 dp，往内容这边多出大约 20 dp 是透明的，手指一按就抓住。惯性滑完拇指还会停一会儿；滑到最底时拇指停在右下角，正好是右手往回滑的起点，于是被当成在拖滚动条：列表按比例跳一下，松手没有惯性。中间滑时拇指不总在同一个地方，所以只是偶尔撞上。你觉得没碰到滑块，是因为碰到的是透明的那一截。现在可点区域收成画出来的那一截；按在拇指上仍是按下就拖。列表、网格、瀑布流三根都改了，番剧详情页剧集网格那一根也改了。这一版没有真机手势测试。折叠屏全景紧凑右边还空不空、滑到底再往回甩还有没有惯性、滚动条变窄之后还能不能稳稳按住拖，要在手机上确认。
- **书架中间有时滑完没有惯性**（preview.19，和 Mihon preview.6 同一处）：上一版收回滚动条热区，只解释「滑到最底再往回滑」那一下。书架不在底部时偶尔还是滑完没有惯性，加宽解释不了。preview.20（补丁 0041）起先记日志，不改滑动手感，与 mihon-harmony 0033 同源。只记全景（瀑布流）网格。日志已经定位，见下一条。
- **往下翻很多之后，往回甩没有惯性**（preview.20，和 Mihon preview.7 同一处）：上一版的日志否定了「触摸送慢了、速度被算成 0」。往下翻都正常；一次往回甩之后，连着几次往回甩的惯性起速都是 0。全景网格自己写的滚动，把「新位置减旧位置」当成已经滚过的距离交回去。滚过大约六万多像素之后小数不够用，每一帧剩下千分之几像素。书架外面的下拉刷新把这一点当成你在下拉，往回甩时就把速度全部吃掉。往下翻不受影响。preview.21（补丁 0042）起，没滚到两头时把真正移动的距离原样交回去，与 mihon-harmony 0034 同源，`PanoramaMasonry.kt` 两边逐字节相同。诊断日志还在。只有全景网格是自己写的滚动。可选升到这一版：往下翻很多之后连续往回甩是否都有惯性；滑到最底再往回甩是否正常。若仍复现，照旧立刻转储崩溃日志。
- **惯性修好了，滚动条又很难按到**（preview.21，和 Mihon preview.8 同一处）：上上版为了不误抓往回甩，把滚动条能按的范围收回到画出来的那一条（约 12 dp），手指很难按中。preview.22（补丁 0043）起能按的范围恢复到约 32 dp，分两段：按在画出来的那一条上立即抓住；旁边那一截要按住不动约 0.12 秒才抓，快速一甩照常滚内容、有惯性。惯性滚动中按下去只是停住，不会抓。列表、网格、瀑布流，加上番剧详情页剧集网格的 `IrregularVerticalGridFastScroller`，四根都改了。已知副作用：在滚动条旁边一动不动按住半秒以上，仍可能弹出条目的长按菜单。与 mihon-harmony 0035 同源。
- **想知道上下滑为什么有时卡、有时顺**（preview.22，和 Mihon 相同）：preview.23（补丁 0044）起加了调试开关：设置 → 高级 →「滚动性能记录（调试）」，默认关。打开后左下角出现半透明的「记录」按钮，觉得卡的时候马上点一下，在分享面板里把 `anikku_scroll_perf_<时间>.txt` 发出来即可，不需要 IP、token 或电脑。文件里只有数字（每帧各阶段耗时、帧间隔、全景网格每帧测量次数、GC / CPU / 刷新率 / 温控 / 省电模式、卓易通图形层报错的每秒条数、滑动轨迹），不含书名、网址、扩展列表和 logcat 原文。开着会多一点耗电，用完关掉。与 mihon-harmony 0036 同源。
- **下载的画质一直跟正在播放的画质一样**（preview.15）：队列里没有单独指定视频的剧集，下载器和播放器取的是同一条——扩展标成首选的那一档。扩展自己分不出「这是播放还是下载」。以前只能在作品页长按某一集，选「选择视频画质」，一集一集选。preview.16（补丁 0029）起：设置 → 下载 →「下载画质」，在「并发下载」那条滑块下面，默认「最高可用」。还可以选不超过 2160p、1440p、1080p、720p、480p、360p，或者「与播放相同」（继续用插件的首选）。没单独选过画质的剧集按这个下；在线播放仍用插件里的首选画质。某一集已经长按选过的，仍以那次为准。插件只给一种画质时（例如 RouXun 只有一条 HLS）设了也没有区别。Mihon 是漫画，没有这一项。Animeko 播放和缓存共用一套分辨率偏好。

**鸿蒙图库会收录下载的视频。** 卓易通把应用选的 SAF 文件夹映射到鸿蒙文件管理的「我的手机 → 兼容应用数据 → …」下，
鸿蒙的媒体扫描会把整棵树扫一遍，并且**不认 `.nomedia`**（华为官方文档也只说图库按文件类型收录）。它判断“是不是视频”只看扩展名，
所以本构建从 preview.2 起把下载完成的视频存成 `<集>.mkv.anikku`：对系统来说是“未知类型文件”，图库不收；Anikku 自己是通过文件描述符交给 mpv 播放的，
不看扩展名，播放完全不受影响。想在别的播放器里打开，把末尾的 `.anikku` 去掉即可。

## 下载与安装

- 到 [Releases](../../releases) 下载最新的 `Anikku-<tag>-arm64-v8a.apk`（华为设备均为 arm64）。
- 包名为 `app.anikku.beta`，与官方 Anikku Preview **相同但签名不同**：第一次安装前必须先卸载官方 Preview。
  卸载前先在 设置 → 数据与存储 → **创建备份** 导出备份文件，装好本构建后再 **恢复备份**；已下载的视频留在原来的文件夹里不会丢，重新选择同一个存储位置就会被重新识别。
- harmony-preview 版本之间可直接覆盖安装；应用内「检查更新」已改为检查本仓库的 Release，不会再提示安装官方 APK。
  preview.3 起点「下载」后页面会留在原地显示进度，下载完按钮变成「安装」，点它交给系统安装器（和 Mihon 一样）；
  之前那种点完就退回、只靠通知栏和静默安装的流程在卓易通里什么都看不到。
  preview.4 及之前进更新页会直接卡在「正在下载… (0%)」：「检查更新」顺手排了一个 10 分钟后才跑的后台自动下载任务，
  更新页把它当成了自己的下载。preview.5 起不再排这个后台任务（卓易通里它本来也装不上），
  更新页只认自己发起的下载；装完后残留在缓存里的 `update.apk` 会在下次启动时自动删除。
  preview.6 起更新相关的界面与 Mihon 完全一致：装完新版第一次启动不再弹「已更新至 vX」对话框，关于页的「更新日志」改为直接打开当前版本的 Release 网页
  （KMK 原来的「更新日志」页面写着「最新: v…-preview.N – 当前: …-harmony.N」，刚装完 N 看起来就像又在推送 N）；
  已是最新时点「检查更新」提示「没有新版本」，和 Mihon 一样。
  preview.6 及之前点「下载」后仍会停在「正在下载… (0%)」、按钮灰掉：KMK 把更新下载排成 WorkManager 的 **expedited（加急）任务**，卓易通从不派发这种任务，
  worker 根本没跑起来。preview.7 起改成和 Mihon 一样的普通任务；更新页还会清掉上个版本遗留的、从未开始的下载请求，点「下载」20 秒内没动静则变回「重试」。
  preview.8 及之前点「下载」后，更新页上的版本说明会随进度一直闪烁 / 短暂变空：进度每跳一次页面就重绘一次，KMK 每次都新建一个 Markdown 解析器配置，
  渲染库把它当成「内容变了」重新解析一遍。preview.9 起解析器配置只建一次（Mihon 上游本来就是这样写的），说明文字在下载期间保持不动。
- **「检查更新」报「HTTP error 403」**：不是仓库权限问题。更新检查以前直接请求 `api.github.com`，GitHub 对匿名请求的配额是**每个出口 IP 每小时 60 次**，
  手机走运营商 NAT 或代理时这 60 次是和同一出口的所有人共用的，用完就是 403，一小时后自动恢复（换个网络即换 IP 也行）。
  preview.7 起更新器优先读本仓库 `repo` 分支上由流水线生成的 Release 索引（`raw.githubusercontent.com/Xun2202/anikku-harmony/repo/releases.json`，普通 CDN，没有这个配额），
  读不到再退回 GitHub 接口；同时修掉 KMK「已是最新时不记录检查时间、每次启动都重新检查」的问题。
  索引有最多约 5 分钟的 CDN 缓存，刚发版就点「检查更新」可能要等几分钟。
- 后台下载：卓易通会在 App 切到后台几秒后冻结进程，下载队列和番剧库更新都会停住。preview.3 起默认开启 设置 → 下载 →「**后台保持运行（鸿蒙）**」：
  下载 / 更新期间播放一段静音音轨并持有唤醒锁，卓易通就不会冻结进程；不影响其他 App 的声音，不需要时可关闭。
  关闭后回到官方行为，另受 Android 15 的限制：数据同步类前台服务后台累计 6 小时会被系统强制停止（表现为闪退），隔几小时切回前台可重置额度。
- 下载通知（preview.4 起）与 Animeko / Mihon 的鸿蒙版统一：标题「正在下载 N 个剧集」，正文「下载：<速度>/s · <进度>%」+ 进度条，
  下拉展开显示当前的「番剧 - 剧集」（开启「隐藏通知内容」时不显示）。ffmpeg 还没报出百分比（或视频时长未知）时只显示速度和滚动进度条。
- **存储位置**：继续用 `Documents/Anikku` 这类自选文件夹即可（和 Mihon 一样，换机、重装都方便）。
  设置 → 下载 → 「**下载的视频对系统图库隐藏**」默认开启，新下载会存成 `<集>.mkv.anikku`，鸿蒙图库不再收录。
  升级前已经下载的 `.mkv` 还是旧名字，点一下同一页的「**按上述设置重命名已下载的视频**」统一补上后缀（下载进行中时不能点，先暂停）。
- 不想在文件管理里看到任何下载内容的话，也可以选 设置 → 数据与存储 → 「使用应用私有目录（鸿蒙推荐）」：下载保存到 `Android/data/app.anikku.beta/files/Anikku/`，
  不经过 SAF；代价是卸载应用时会一并删除，自动备份也在里面，卸载前记得导出。
- **同一视频收藏进多个文件夹**（XvXun 这类把收藏夹当“剧集”的源）：设置 → 下载 → 「**不同条目间共用已下载的视频**」默认开启，
  一个视频只要在同一来源的任一条目下载过，其他条目里也显示为已下载并直接播放那份文件；「下载未看/下载后 N 集」也会跳过它们。
  删除时请到真正下载它的那个条目里删——在别的条目里点删除不会有效果（文件不属于它）。
- **横版封面（XvXun 这类 16:9 缩略图的源）**：书架 → 筛选 → 显示 → 显示模式 选「**全景松散网格**」。preview.7 及之前这个模式只是把 16:9 的图塞进
  2:3 的竖格子里，上下留两条看不见的空边，封面反而更小；preview.8 起书架的格子按 3:2 横版排（和「浏览」页的全景网格一样），封面铺满格子、一行仍是同样的列数。
  源目录 / 浏览页的全景网格、条目详情页的「全景封面」（设置 → 外观）原本就正常，不受影响。
- **下载到 100% 后变成「!」**（preview.7 及之前）：进度条只反映 ffmpeg 写完视频这一步，之后还要把视频搬进下载文件夹。卓易通的文件夹不支持改名，
  原来的三次改名在那里实际上是**把整段视频再抄三遍**（`.tmp` → `.mkv.anikku` → `<集>_tmp/` → `<集>/`），期间看起来卡在 100%，任何一步失败就变成「!」，
  而且既没有可见的通知也没有日志能说明原因。preview.8 起：视频直接以最终文件名写入（只多一个空的 `.tmp` 标记文件），目录改名优先用系统的「移动」
  （不经过 App 复制），都失败才复制，并自动重试两次；已经下好的视频会留在私有缓存里，点「!」重试不会重新下载。
  下载队列里出错的条目会在集名下面直接显示原因（ffmpeg 的最后几行报错 / 目录里多了什么文件 / 「下载被中断」），不用再导日志。
- APK 被交给「出境易」而提示「暂不支持安装该应用」时，把 APK 复制到本机存储后用系统「文件管理」打开即可由卓易通安装（详细步骤见 [animeko-harmony 的说明](https://github.com/Xun2202/animeko-harmony#安装步骤鸿蒙-next--6--7)，两者相同）。

## 版本号规则

- `versionName` = `<官方版本>-harmony.<N>`，例如 `0.2.0-harmony.1`；preview 构建类型会再自动追加 `-<上游提交数>` 后缀，这是 Anikku 自己的行为。
- `versionCode` = `<官方 versionCode> × 100 + N`（如 `8 × 100 + 1 = 801`），保证新官方版本的任意 harmony 构建都高于旧版本的，覆盖安装不会被拒。
- Release tag = `<官方 tag>-harmony-preview.<N>`。`N` 是同一官方版本的第几次打包，改了补丁需要重发时递增。**不要改这个格式**，更新器靠它识别版本。
- Release 必须是正式 Release（非 prerelease）：Anikku 的更新器会过滤掉 prerelease。

## 构建机制

流水线定义在 [`.github/workflows/harmony_preview.yml`](./.github/workflows/harmony_preview.yml)，每天 UTC 04:23（北京 12:23）定时运行，也可以在 Actions 里手动触发并指定 `upstream_tag` / `patch_number`，或勾选 `dry_run` 只编译不发布：

1. 取官方最新稳定版 tag（或手动指定），若对应 Release 已存在则直接结束。
2. `git clone --branch <tag> --single-branch` 官方源码（保留完整历史，preview 构建用提交数做版本后缀）。
3. [`scripts/prepare-source.sh`](./scripts/prepare-source.sh)：按 `series` 顺序 `git apply --3way` 补丁、改写 `versionCode` / `versionName`，每一步各提交一次。
4. JDK 17（与官方 `build_preview.yml` 一致），`./gradlew assemblePreview -Penable-updater`（不带 `-Pinclude-telemetry`，因此不需要官方的 `google-services.json`）。preview 构建类型用 debug 密钥出包。
5. 用 `zipalign` + `apksigner` 以仓库 Secrets 里的密钥重签 `arm64-v8a` 与 `universal` 两个 APK，命名为 `Anikku-<tag>-arm64-v8a.apk` / `Anikku-<tag>.apk`，上传为 Actions artifact 并 `gh release create`，Release 说明里附 SHA-256。
6. [`scripts/write-release-index.sh`](./scripts/write-release-index.sh) 把 `GET /repos/<repo>/releases` 全部分页的条目（字段原样，按 `created_at` 倒序取前 30 条；接口本身的顺序不按创建时间）写到孤儿分支 **`repo`** 的 `releases.json`（另附 `latest.json`），
   应用内更新器（0014 起）优先从 `raw.githubusercontent.com/Xun2202/anikku-harmony/repo/releases.json` 读它。`GITHUB_TOKEN` 创建的 Release 不会触发别的 workflow，所以发版流程自己调用这个脚本；
   手动增删改 Release 时由 [`.github/workflows/release_index.yml`](./.github/workflows/release_index.yml)（`release` 事件，也可手动触发）重新生成。`repo` 分支只放这三个自动生成的文件，不要手改。

[`.github/workflows/check_patches.yml`](./.github/workflows/check_patches.yml) 在补丁改动时和每周一，把补丁分别试套到官方最新稳定版和 `master`，上游一变就能提前知道要 rebase。
